# Assessment runtime and orchestration audit

**Scope:** read-only inventory of the current `deepagents` assessment path against `docs/architecture/agentic-production-implementation-plan.md` (especially §§4, 9–18, 21–22, 26). The production plan is treated as the target. No source files were changed and no tests/builds were run.

## Current production path

`scan_requested` enters `RepositoryAnalysisBoundary.handle`, which calls `RepositoryDeepAnalyzer.analyze` for a separate bounded AI-discovery pass and posts a scan callback. `engineering_assessment_requested` enters `InterviewGatedEngineeringAssessmentBoundary`; `_prepare_interview` loads persisted Interview state, applies Scanner/PGE and technical-coverage gates, and may require an Initial Interview before any rule work. Once admitted, `EngineeringAssessmentBoundary._assess` resolves/recovers rules, evaluates applicability, iterates eligible rules, and calls `analyze_rule`; that function launches a fresh direct Repository Analyst task/thread per rule and attempt. `finalize_rule_results` then converts accepted criteria to claims, calls the deterministic `EngineeringRuleEvaluator`, applies the rule-completion gate, and returns a callback.

Customer answers take a separate path: `AssessmentInterviewResumeBoundary.handle` reloads/validates the Interview thread and revisions, runs the Interview subagent, persists its decision, writes a `PostGuardContinuationStore` record, then resumes the originating rule through `_resume_rule` and `EngineeringAssessmentBoundary.run_assessment`. Targeted requests enter `TargetedRepositoryAnalysisBoundary.handle`, validate an authorized `ruleScope`, then call the same boundary for one EngineeringRule.

## Deep Agents capabilities already available

The target plan names native root agent/tool iteration, adaptive calls, `task()` delegation, per-subagent tools/models/middleware, filesystem working memory/offload, long-context compaction, LangGraph checkpoint and interrupt/resume, shared thread continuity, middleware composition, optional `TodoListMiddleware`, structured tool/response contracts, and skill/instruction loading.

This checkout already uses `create_deep_agent`, a LangGraph `checkpointer`/`store`, `TodoListMiddleware`, and middleware composition in `deepagents/agent.py`. But assessment orchestration is explicitly prohibited in `instructions.md`: root tasks are restricted to Legal Triage. `repository-analyst` and `interview` are defined but not configured in the root's native `subagents=` list; `RootSubagentDispatcher.dispatch` reconstructs and invokes each specialist directly. The Python assessment loop, separate Interview thread, and hand-built continuation/reconciliation state therefore own planning and resumption that the target assigns to the Root checkpoint.

## Explicit findings

- **One rule = one agent assumption:** present in `repository_analyst/definition.py` prompt/description; `_assess` loops over each rule; `analyze_rule` creates a unique one-rule context/thread per attempt; a resumed business need is bound to one originating rule and `_resume_rule` re-enters that rule. The target keeps one decision record per rule if useful, but removes per-rule reasoning threads and reuses evidence across rules.
- **Duplicate planning:** there is no active Planner or Investigator subagent in `deepagents/subagents`. The custom planner is the deterministic order/gating work in `EngineeringAssessmentBoundary._assess` plus applicability pre-evaluation; `TodoListMiddleware` already supplies native optional task planning. Replace semantic sequencing with Root reasoning and retain only deterministic coverage/finalization checks.
- **Duplicate context:** authoritative customer facts live in the API, while interview-private context is separately projected through `ConfirmedStructuredBusinessContext`, a currently uncalled `ConfirmedContextPack`, per-rule prompt strings, and per-run context fields. Use the API as domain authority and Deep Agents working memory as non-authoritative working context.
- **Duplicate resume/state:** LangGraph checkpointer/store already exist in `create_root_agent`; current Interview state, per-rule workflow IDs, post-guard continuation rows, JSON waiting-assessment registry, and exact-rule replay form parallel execution state machines. Keep authoritative API records, outbox/leases, optimistic revisions, and idempotency; remove the parallel semantic state machines.
- **Compatibility / legacy:** `EngineeringRuleService.get_or_compile` says its name remains temporarily for caller compatibility and reads cache/precompiled bundles; `EngineeringRuleEvaluator` has a legacy no-`required_evidence` fallback; `confirmed_business_context` accepts historical field aliases. Retire these with their consumers under the new contracts. `request_targeted_reanalysis` has no production definition/registration in this checkout (only negative registry assertions); do not add an agent-callable reanalysis tool. Planner/Investigator names are residual skill/document vocabulary, not active assessment subagents.
- **Do not remove trust guards with the semantic pipeline:** preserve pinned repository/legal versions, tool authorization, tenant context, evidence minting/verification, source provenance, stale-revision rejection, idempotency, checkpoint persistence, cancellation/pause, outbox reliability, and Completion Gate.

## Target mapping summary

`create assessment + pin/hydrate/index → Assessment Root on one durable checkpoint → optional generic Repository Researcher via native task() → root-authored applicability and RuleDecisions → deterministic DecisionValidator + coverage ledger + Completion Gate → final report`.

A human answer becomes a governed fact update and resumes that same Root checkpoint. A targeted retry remains a server-owned `ruleScope` request and targets the same Root assessment state. Legal Preparation remains a separate agent and never receives Assessment/customer/repository context.
