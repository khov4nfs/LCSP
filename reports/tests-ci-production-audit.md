# LCSP production verification audit and plan

**Scope:** read-only inventory of tests, CI workflows, Prisma migrations, and verification gaps against `docs/architecture/agentic-production-implementation-plan.md` and the stated acceptance criteria.

**Finding:** current proof is **PARTIAL** for the target architecture. The repository has good API, Postgres, checkpoint, outbox, provenance, and replay coverage for the current Interview/per-rule implementation; those are useful test seams, but the production vertical uses scripted agents and deterministic applicability/completion decisions. It does not prove the planned Legal Preparation Agent, single assessment Root Agent, agentic applicability/compliance, or final V2 completion contract. No tests, CI jobs, migrations, or deployment checks were run in this read-only task; existing untracked files were left untouched.

## Required new production suites

1. **Legal Preparation portfolio vertical + semantic evals.** From a pinned corpus version through the Legal Preparation Agent, validate and atomically activate a complete LegalRule + EngineeringRule portfolio without approval. Integration cases must preserve definitions, scope, exceptions, qualifiers and cross-references; generate non-repository obligations; reject fabricated/stale refs and duplicate IDs; and prove a failed/partial run leaves the old ACTIVE portfolio intact. Expert-reviewed evals score extraction coverage, omissions/duplicates, rule generation, context preservation and legal strength; deterministic unit tests check only trust/integrity.
2. **Assessment Root Agent vertical.** Use the production API, DB, checkpointer, outbox and built runtime image with a synthetic tenant and pinned repo/corpus. Prove the Root owns the whole assessment, covers every active EngineeringRule, reuses evidence across rules, emits provenance-bound decisions, and produces a frozen report only after completion. A test model may make boundary E2E repeatable; separate model-backed evals must prove semantic quality.
3. **Agentic applicability/compliance eval suite.** Run expert-labeled cases for applicable/irrelevant obligations, criteria MET/NOT_MET, compliant/non-compliant decisions, organizational duties, question necessity, bounded absence, evidence reuse, and adversarial/fabricated refs. Require 100% rule coverage on the fixture set, zero accepted fabricated/stale/cross-tenant evidence, and zero final UNKNOWN/PARTIAL. Legacy evaluators may be shadow metrics during a bounded comparison window, never an override.
4. **Native HITL/restart E2E.** Root investigates first; only a material unresolved fact creates a HumanResolutionRequest. Restart the worker/runtime while interrupted, answer and resume the exact assessment checkpoint, assert no duplicate question/decision, preserve accepted evidence/context, reject a foreign need/revision, and prove “I do not know” stays unresolved and blocks finalization. Include Playwright coverage of the real user answer/confirmation flow.
5. **Assessment and memory isolation suite.** Use unique canary facts in A, then start B under same user, same tenant/different user, different tenant, same repository, and same legal portfolio; prove B cannot retrieve, emit, cite, or authorize A’s data. Cover researcher/subagent boundary, unique server-owned thread/checkpoint namespace, concurrent starts, deletion/retention, prompt-injection into shared learning, and rejection of memory as evidence. This is the production form of plan M1–M8; the existing thread-ledger tests are insufficient.
6. **Completion/final-report gate suite.** Unit-test deterministic requirements: every in-scope EngineeringRule has exactly one final applicability/compliance disposition; applicable rules have all mandatory criteria and valid evidence; no unresolved HumanResolutionRequest, stale case/repo/legal version, invalid artifact, or missing coverage remains. Negative integration test injects one unresolved item and proves report endpoint/job cannot run; positive test freezes accepted state then emits a report with no open-question/UNKNOWN/PARTIAL placeholders.
7. **Reliability/concurrency/upgrade suite.** Concurrent assessment creation and portfolio activation; duplicate outbox/tool/answer delivery; one active Root lease; provider/model failure; interrupted/restarted subagent; checkpoint corruption and recovery; portfolio update invalidating only affected decisions; repository snapshot change; restore from backup. Assert lifecycle and evidence remain coherent and failures never become legal verdicts.

Use the architecture plan’s mandatory end-to-end scenarios A–L as the core scenario matrix (repository-only complete, irrelevant rule, fact-blocked applicability, “I do not know”, document/organizational duty, bounded absence, evidence reuse, pause/resume, restart during HITL, portfolio change mid-run, provider failure, completion-gate negative). Add memory-isolation M1–M8 and production reliability cases as separate release suites.

## Migration, CI, and production verification plan

- **Forward-only expand/backfill/cutover/drop.** Add V2 portfolio/version/activation and AssessmentCase/Evidence/coverage/RuleDecision/HumanResolutionRequest records with tenant-scoped FKs, pinned source versions, revision rules, idempotency keys, and unique server-owned Root thread identity. Backfill from V1 rows using explicit mappings for history only; do not translate `UNKNOWN` or old status into a new legal decision. Decide/test how open V1 cases are terminalized or migrated before switching readers. Run both clean-install and populated V1-to-V2 upgrade fixtures, prove idempotent/restartable backfill and preserved artifacts, then drop obsolete tables in a later migration after V2 is authoritative. Keep old SQL migrations in history.
- **Migration CI.** Keep `prisma migrate deploy` on an empty disposable Postgres DB. Add a second job that starts from a production-shaped V1 schema with representative corpus, rules, assessment, thread, event, evidence and open-question rows, applies the full migration chain, and asserts records, tenant boundaries, uniqueness, constraints, indexes, and resumable checkpoint identity. The present `api-e2e` and LCSP-278 vertical use guarded `db push`; they do not replace an upgrade migration test. Keep all destructive operations behind the disposable DB guard.
- **Required PR checks.** Keep the path-filtered API/Python/static checks, and make the new V2 migration-upgrade suite, legal-preparation vertical, Root production vertical, completion negative gate, isolation/restart suite, and UI Playwright flow required on any affected area. Rename the LCSP-278 job and seed after replacing their V1 contracts. Add a model-backed agent-eval workflow for trusted branches/release candidates (and scheduled/manual regression), using pinned model/version and reviewed fixtures so untrusted PRs do not need production credentials.
- **Pre-release/staging proof.** Deploy the built production runtime and API against a restored/synthetic tenant dataset; verify migration status, health/readiness, automatic portfolio activation, complete repository-only case, HITL interrupt → worker restart → same-thread resume, completion rejection while unresolved, and report acceptance after all decisions. Retain sanitized logs/correlation IDs only; do not use customer facts in canaries.
- **Post-deploy production proof.** Run read-only migration/health/runtime checks plus a synthetic isolated assessment canary; verify no legacy route/fallback is serving, portfolio pin and completion gate are active, and the canary is deleted/retained per policy. This task did not perform production or browser verification.

**Release decision for target:** **PARTIAL / NOT READY to claim final-architecture E2E proof** until the V2 agent evals, migration-upgrade path, same-thread HITL restart, cross-assessment canaries, and completion-gate negative E2E pass. The current production vertical is reusable infrastructure coverage, but its scripted specialist and V1 stage semantics are not sufficient acceptance evidence.
