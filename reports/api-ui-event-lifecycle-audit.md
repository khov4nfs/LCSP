# Assessment lifecycle authority audit

**Scope:** `apps/api`, `apps/web`, `packages/contracts`, and runtime event projection. Read-only audit; no source changes or tests.

## Finding

There is no single assessment-level lifecycle authority today. The assessment row carries wizard/setup state and the `AI_NOT_DETECTED` terminal result, while scan jobs, technical evidence reports, interview threads, runtime turns, runtime events, post-finding state, and document requests each own narrower status. The API’s `AssessmentStageLifecycleProjection` is the closest shared stage read model and the sidebar gives it final precedence, but other API and browser code independently derives overall, run, stage, waiting, and continue states.

The canonical target should be one API lifecycle application service/projection builder. It should return an assessment-level lifecycle view (overall status, current stage/run, stop/resume/continue disposition, wait/block reason, terminal outcome, revision/as-of) and be reused by assessment reads and the workspace SSE snapshot. Keep domain-specific records as authoritative facts and their status fields as subresource state; route assessment-level transition policy through the lifecycle boundary. Event history remains activity evidence and detail, not another lifecycle authority.

## Independent derivations and mutations to consolidate

1. **Root status versus stage status:** the assessment aggregate currently advances wizard setup and AI absence, while the contract also advertises scan/classification/review values. Runtime state is instead read from other records. `WorkspaceOverview` counts `READY_FOR_REVIEW`, but no current API setter for it was found.
2. **Interview waiting:** `AssessmentInterviewRuntimeService.pipelineInterviewStatus` treats `state.activeQuestion`, the persisted active-question column, and `BLOCKED_OR_UNRESOLVED` as customer-waiting. `stage-lifecycle.deriveInterview` checks the persisted column and revision counters. These are independent predicates over the same Interview state and can disagree.
3. **Liveness:** `getPipelineLiveness` checks the latest `AssessmentRuntimeTurn` and terminal event/status with an age window. `buildWorkspaceSnapshot` instead marks an assessment live from any recent activity timestamp; `deriveRuleAnalysis` uses that boolean. A recent terminal event can therefore make pending rule work display as running.
4. **Readiness:** `GetAssessmentHandler`, `GetAssessmentReadinessHandler`, and stage derivation independently inspect accepted technical evidence to conclude classification lock, missing evidence, or scanner done/partial.
5. **Browser lifecycle fallback:** `normalizeWorkflowSteps` still assigns stage statuses from event/run/Interview/scan data even though `applyStageLifecycle` is intended to make API lifecycle authoritative. On missing projection data, the browser becomes a second lifecycle calculator.
6. **Event-derived terminal state:** the web computes run and turn outcomes from stream event order even while API run status and `AssessmentRuntimeTurn` control are available. These event projections are appropriate for explaining activity, not for enabling Continue or claiming assessment completion.
7. **Mutation on failed Continue:** pipeline Continue records its customer-continue control event before checking if Interview still owes a customer answer. Central transition policy should validate first or make this ordering an explicit transactional contract.

## Canonical target flow

- One API lifecycle projection builder owns the overall state and current stage/run. It reads assessment status, scan/report facts, Interview state, runtime-control acknowledgement, rule progress, and post-finding outcome.
- Assessment GET/readiness and workspace runtime SSE call that builder; `packages/contracts` defines one lifecycle response shape. Runtime events carry technical detail and wake-up/invalidation signals only.
- Stop, runtime resume, pipeline continue, rerun, HITL answer/decision, and terminal evidence commands keep their domain-specific writes, but use the same lifecycle boundary for allowed transitions and emitted assessment-level lifecycle updates.
- The web consumes this lifecycle response for badges, sidebar stages, screen selection, stop/continue/resume availability, and ready-for-review counts. Event projections remain for activity rows, model/tool detail, and usage display.
- Snapshot reads are pure. Timeout/reconciliation processes perform explicit durable transitions and publish their lifecycle event.
