# LCSP Legal Preparation Inventory (read-only) — KEEP / REWRITE / DELETE

Target: Legal Corpus -> agentic Legal Preparation -> LegalRule + EngineeringRule -> deterministic integrity validation -> automatic ACTIVE portfolio. No human approval. No compat duplicates.

Paths relative to repo root. API = apps/api/src/modules/legal-rule-catalog (abbrev `LRC/`). PY = deepagents/tools.

## 0. Current-state map (what exists today)

Corpus: crawl (`PY/legal/sources/...`) -> `LegalCorpusRecoveryDriver._run_locked` -> API `POST corpus/validated-draft` (`LegalCorpusService.ingestDraft`) -> retrieval index -> automatic activation. The official-source manifest sets `reviewRequired:false, trustPolicy:OFFICIAL_SOURCE_AUTO_TRUSTED`, so that path skips human signoff. Separately, the API's `reviewRequired:true` ingest branch and admin publish route are production-capable human gates; `orchestrate_reviewed_legal_corpus.py` is a manual CLI with no in-repo production caller (see §8).

LegalRule: created *mechanically*, one rule per regex-"candidate" chunk, by `RuleCatalogVersionService.recoverApprovedRulesFromActiveCorpus` (id `AUTO-<corpus>-<chunk>`, family `LEGAL_CORPUS_ENGINEERING_RULE_SOURCE`, sentinel `requiredFacts [{aiDetected: confirmed}]`, written directly as APPROVED). Invoked from `LegalCorpusRecoveryDriver._recover_legal_rule_catalog` and from `rule_sources._recover` (assessment-time).

EngineeringRule: no Prisma `EngineeringRule` model. Assessment resolution uses the Chroma cache (`EngineeringRuleCache`, collection `lcsp_engineering_rules_v1`), falls back to the checked-in precompiled bundle (41 templates and 131 no-rule markers, bundleId `lcsp-vn-2026-08`), and stores recovery artifacts under `recovery-artifacts/engineering-rules|legal-rule-triage`; production Docker images copy the bundle. These are multiple current sources, with no single authoritative relational portfolio.

Triage (LLM, agentic): `triage` subagent + skill `legal-rule-triage` + tools `get_legal_rule_triage_work_items` / `persist_legal_rule_triage_result` / `finish_legal_rule_triage_execution` -> `LegalRuleTriageService.persist_result` -> `EngineeringRuleService.prepare_from_triage` (deterministic gate: `_parse_decisions`, `select_engineering_rule_context`, `validate_engineering_rule`, cache put, artifacts). Triggers: nightly cron prompt (`schedules/legal_catalog_daily.py`), assessment readiness gate (`ENGINEERING_RULE_NOT_READY` -> `LegalRuleTriageBoundary`), operator script `warm_engineering_rules.py`. Global filesystem singleton (`singleton.py`, `middleware/triage_singleton.py`).

Assessment consumption: `rule_sources.resolve_engineering_rules` -> `EngineeringRuleService.get_or_compile` (cache -> no-rule marker -> precompiled bundle -> NOT_READY -> assessment goes WAITING and re-triggers Triage).

"ACTIVE": there is no ACTIVE status. `LegalRuleLifecycleStatus = DRAFT|APPROVED|REJECTED|SUPERSEDED`; "active" = latest APPROVED by `approvedAt/createdAt` (`GetActiveRuleCatalogHandler`, `LegalCorpusService.getApprovedChunks`, `AdminCorpusVersionsService.isCurrentActive`).

## 1. Findings the target architecture must resolve

F1. LegalRule is created by a TS regex term list ("phải", "không được", "bảo đảm"...) — not by an agent. Triage then LLM-demotes most (131 of 172 bundle legal rules => no EngineeringRule). Two competing "normative classification" authorities.
F2. Normative regex is triplicated: `PY/legal/retrieval/legal_basis/normative_chunk_filter.py`, `LRC/application/services/legal-corpus.service.ts` (`legalChunkNormativeClass`, `LEGAL_ENGINEERING_OBLIGATION_TERMS`), `LRC/application/services/rule-catalog-version.service.ts` (`inferNormativeClass`, `normalizeNormativeClass`).
F3. EngineeringRule has no authoritative store. Chroma is a "cache" yet is the only runtime source; bundle is a *second* store; artifacts a *third*. Provenance split across `sourceFingerprint` (sha256 of legalRule JSON + chunk hashes + schema/prompt/compiler version + precompiled contract_version) and `legalRuleCatalogVersionId` / `legalCorpusVersionId` fields that `_retarget_cached_rules` rewrites in place when the catalog version changes (fingerprint intentionally ignores corpus version id — `fingerprint.py` does `_ = legal_corpus_version_id`).
F4. Human-approval assumptions live in `approveVersion`/`ApproveRuleCatalogVersionHandler` + `RuleApprovalRecord`; DRAFT LegalRule + `DraftLegalRuleHandler`; `requireApprovedReviewSignoff`; admin `publish/discard`; and `humanLegalSignoffRequired: True` in EngineeringRule `legalReasoningContract` (`REQUIRED_VALIDATION_POLICIES`, enforced by `validate_legal_reasoning_contract`). The recovery factory also writes a `RuleApprovalRecord` using `LEGAL_RULE_RECOVERY_SERVICE`, so that record is not, by itself, evidence of human approval. Triage `NEEDS_INPUT`/"review-needed" is another legacy human handoff semantic.
F5. Duplicate EngineeringRule generation paths: (a) Triage -> `prepare_from_triage` (live), (b) `EngineeringRuleCompiler.compile` (LLM, dead: no caller), (c) precompiled bundle `materialize` (fallback at assessment time), (d) `import_lcsp_precompiled_engineering_rules.py` (dead, broken imports `tools.legal.legal.*`), (e) `restore_engineering_rule_artifacts.py` (cache restore from artifacts), (f) `get_or_compile` (name says compile, only reads).
F6. Duplicate LegalRule creation paths: auto-recovery (live), `DraftLegalRuleCommand` (manual DRAFT), `author-law-134-baseline-catalog.ts` (manual DRAFT, approval hard-blocked), `restore-legal-corpus-artifacts.ts` (upsert APPROVED from artifact), `seed_legal_rules_dev.py` (raw SQL, DEV-ER-*), `seed-lcsp-278-release-vertical.ts` (test seed).
F7. AUTO LegalRules carry a meaningless applicability contract (`aiDetected = confirmed` for every rule); real applicability is delegated to `RuleApplicabilityEvaluator` over that sentinel. LegalRule today is just a chunk pointer + sentinel.
F8. Precompiled bundle is checked in and COPY'd into prod images; `PrecompiledEngineeringRuleRegistry` validates `bundle.compilerVersion/promptVersion == COMPILER_VERSION/PROMPT_VERSION` where those constants live in the *dead* `compiler.py`. Overrides file (`...contract-overrides-vn-2026-08.json`) is not in repo => always "base".
F9. Assessment path can trigger legal recovery (`rule_sources._recover` -> `LegalCorpusRecoveryDriver`) and Triage dispatch — legal preparation is not isolated from the assessment runtime.
F10. `ENGINEERING_RULE_NOT_READY` + `WaitingAssessmentRegistry` + resume machinery exist only because EngineeringRules are lazily/on-demand prepared. Target (automatic ACTIVE portfolio before assessments) removes the need.

## 3. CONTEXT_ONLY handling (end-to-end today)

1. Structural: TS `legalChunkNormativeClass` / PY `legal_chunk_normative_class`: EXCLUDE_FROM_DATABASE (heading/preamble, dropped at ingest), CONTEXT_ONLY (scope/definitions/principles/state-policy article titles, and any chunk lacking an obligation verb), ENGINEERING_RULE_CANDIDATE (verb present). Stored in `chunk.hierarchy.normativeClass`.
2. Mechanical LegalRule creation keeps only the CANDIDATE class chunks (`recoverApprovedRulesFromActiveCorpus`) — CONTEXT_ONLY chunks never get a LegalRule, but they are still retrievable and are pulled in as parents/references by `retrieve_exact_context` for Triage context.
3. Triage re-classifies every chunk of a rule's context as CANDIDATE|CONTEXT_ONLY|REJECT; `_parse_decisions` forces completeness; only CANDIDATE that also passes the regex veto yields EngineeringRules; CONTEXT_ONLY adds vocabulary only.
