Authority: `docs/architecture/agentic-production-implementation-plan.md` §6–7, §26, Phase 0/1.
No source was modified. No compatibility aliases are proposed: every REPLACE/DELETE means the old value set is removed and callers move to the canonical target.

## 0. Canonical target (from plan)

| Family | Values | Only writer |
|---|---|---|
| **ALS** AssessmentLifecycleState | CREATED, PREPARING, ACTIVE, WAITING_FOR_HUMAN, WAITING_FOR_REQUIRED_INPUT, PAUSED, FINALIZING, COMPLETE, BLOCKED, FAILED, CANCELLED | Runtime Coordinator (API boundary), Completion Gate, Human Resolution svc, pause/cancel cmds |
| **AES** AgentExecutionState | QUEUED, RUNNING, INTERRUPTED, PAUSED, SUCCEEDED, FAILED, CANCELLED | runtime infra, shared by Root/LegalPrep/every subagent |
| **DRS** DecisionResolutionState | PENDING, INVESTIGATING, WAITING_FOR_INPUT, RESOLVED, INVALIDATED | coverage ledger |
| **ALCS** ArtifactLifecycleState | BUILDING, ACTIVE, SUPERSEDED, INVALID (+FINAL publication) | artifact owner |
| Decision *data* (not state) | applicability APPLICABLE/NOT_APPLICABLE; criterion MET/NOT_MET; compliance COMPLIANT/NON_COMPLIANT/null | Root via `submit_rule_decision`, validated |
| HumanResolutionRequest.status | OPEN, RESOLVED, SUPERSEDED, CANCELLED | Human Resolution svc |
| Fact authority / evidence | REPOSITORY/CUSTOMER/DOCUMENT/RUNTIME_CONFIRMED, LEGAL_AUTHORITY; evidence `verificationState` | evidence ledger |
| Events | one canonical event envelope; detail = activity/event, never lifecycle | runtime |

Kind legend: **L**=lifecycle, **E**=execution, **D**=decision, **A**=artifact, plus **F**=fact/evidence, **V**=event/observability, **X**=out of scope (infra/billing/auth/legal-ingestion, keep).

Abbreviations: `C`=packages/contracts, `API`=apps/api, `Web`=apps/web, `Py`=deepagents (Python worker), `Pr`=Prisma.

## 8. Duplicated-state hot spots (why component state machines exist today)

1. **Assessment progress is split across five representations:** `AssessmentStatus` (aggregate value), `AssessmentRuntimeControlState` (run control), `AssessmentRuntimeRunStatus` (execution), `ASSESSMENT_STAGE_LIFECYCLE_STATES` (derived projection), and `REPOSITORY_SCAN_JOB_STATUSES` (job execution/input result). Web then re-derives presentation states (`NORMALIZED_WORKFLOW_STEP_STATUSES`, `ASSESSMENT_SIDEBAR_STATUSES`, `AGENT_STREAM_TURN_STATES`) from these sources. They are not five equivalent lifecycle machines; the fix is one ALS plus separate AES/DRS/ALCS and view-only projection.
2. **Lifecycle derived instead of stored:** `stage-lifecycle.ts` computes scanner/interview/ruleAnalysis/gate states from scan jobs + evidence reports + interview thread + engineering progress; `isLive` heartbeat decides RUNNING vs CLAIMS_PARTIAL; web `assessment-runtime-adapter.ts` re-maps again.
3. **Python/TS mirror drift:** `rule_assessment/values.py` mirrors C by hand; `ENGINEERING_RULE_EVALUATION_STATUSES` duplicated in Py; `handoffs.py` uses raw `Literal[...]` strings (violates AGENTS.md value-set rule); `waiting_assessments.py` holds a private file-based "waiting" checkpoint store.
4. **Decision conflated with state:** `NEEDS_CONTEXT`, `UNKNOWN`, `UNRESOLVED`, `BLOCKED_UNKNOWN_FACT`, `UPSTREAM_FACT_PENDING`, `AI_UNKNOWN` are not final assessment outcomes. Preserve their unresolved meaning in DRS `INVESTIGATING` while evidence work continues, DRS `WAITING_FOR_INPUT` plus HumanResolutionRequest for a material external fact, or AES failure for execution/provider failure. Only an unobtainable required dependency maps the assessment to ALS `BLOCKED`; unknown never becomes `NOT_APPLICABLE` by default.
5. **Human approval modeled as state** (`PENDING_APPROVAL`, `APPROVED`, `PENDING_CUSTOMER`, legal `APPROVED/REJECTED`, `PENDING_INDEPENDENT_REVIEW`) contradicts §1.2/§1.4.
6. **UI infers business state:** web projections use local values such as `running`, `completed`, and `paused` to describe business progress. Replace those inferences with server ALS/AES/DRS; retain genuine view/loading/connection states as local UI state, where lowercase values are allowed.

## 9. Architecture decisions closed against the plan

- `BLOCKED` means a required dependency is unobtainable under the current assessment contract after the available governed resolution path is exhausted; it has no final report. An open human request remains `WAITING_FOR_HUMAN`; a document/runtime input that can still be supplied remains `WAITING_FOR_REQUIRED_INPUT`; preparation or provider work that can be retried remains `PREPARING`/`ACTIVE` with AES execution state; unrecoverable runtime/system failure is ALS `FAILED`, not `BLOCKED`.
- Plan §6.1 fixes the meaning of `BLOCKED` but does not name its reason codes. Use this closed `AssessmentBlockReason` vocabulary only on ALS `BLOCKED`: `HUMAN_FACT_UNRESOLVABLE`, `REQUIRED_DOCUMENT_UNAVAILABLE`, `REQUIRED_RUNTIME_INPUT_UNAVAILABLE`, `LEGAL_PORTFOLIO_UNAVAILABLE`, `REPOSITORY_SNAPSHOT_UNAVAILABLE`. Add scoped references (`humanResolutionRequestId`, input/document ID, portfolio version, or snapshot ID) and safe detail as fields, not new reason or lifecycle values. Credit shortage is billing/execution metadata, not an assessment blocker. Stale but refreshable legal/snapshot inputs remain in `PREPARING`; use the corresponding unavailable reason only when the pinned dependency cannot be restored under the contract.
- `PAUSED` is the lifecycle state for an explicit user/runtime pause. The same root execution is AES `PAUSED`; a LangGraph/tool interrupt is AES `INTERRUPTED` and the Assessment lifecycle determines whether the reason is human input, required input, or another blocker. Stop/resume requests are commands/events, not states.
- `AI_NOT_DETECTED` remains a decision result (all relevant EngineeringRules are `NOT_APPLICABLE`), never a terminal lifecycle value. The Completion Gate authorizes `FINALIZING`; `COMPLETE` follows successful final artifact persistence.
- Post-finding remediation analysis and recommendations belong to the Assessment Root Agent and final report. Code change execution, PR status, and PR approval belong to the repository's normal change-management/GitHub owner and policy, outside the assessment lifecycle. Assessment completion does not wait for a PR or human approval; an unresolved fact that changes a compliance decision must be resolved before the Completion Gate.
- The plan mandates one canonical event envelope but leaves its serialized shape open. §11 closes the minimum shape while preserving event ordering/deduplication, trace correlation, activity detail, and the sole ALS writer.

### Canonical assessment event envelope

The one persisted/streamed envelope is a discriminated union with common metadata:

```text
AssessmentEvent = {
  eventId, assessmentId, executionId?, sequence, occurredAt, correlationId,
  payload:
    | { kind: ACTIVITY, activity, details? }
    | { kind: EXECUTION_STATE_CHANGED, state: AgentExecutionState }
    | { kind: ASSESSMENT_LIFECYCLE_CHANGED, lifecycleState: AssessmentLifecycleState,
        reason?: AssessmentBlockReason, assessmentRevision }
}
```

`eventId` is the idempotency key; `sequence` is monotonically allocated per assessment in the event authority for deterministic ordering; `correlationId` links one command/agent operation across callbacks. Activities may identify tool, model, agent, or domain action but carry no implied lifecycle state. `reason` is present only on a `BLOCKED` lifecycle transition. Only the plan's transition owners may emit accepted lifecycle changes, and their transaction persists the Assessment revision and corresponding event together. UI and downstream projections consume events but never infer or write ALS from a stage/activity/status label.
