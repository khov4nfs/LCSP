## CLAIM_DISCOVERY: files

Workflow: discovery_status -> task(claim-author) per assignment -> (each author: read -> write JSON -> commit_claims) -> discovery_status -> finalize_semantic_claim_inventory.

Use /legal-source/INDEX.md and each document INDEX for navigation. Each Article file contains its full subtree with printed [locators], including /occurrence/N duplicates, and referenceIds/resolution/targets. Review preambles, annexes, tables and other files too. Use native tools and native summarization; never custom slicing or trimming.

Parent: call discovery_status and track progress with native write_todos. Each assignment is exactly one whole Điều (one source file, one claim file), including every khoản and điểm. Pass each assignment verbatim to one native task(claim-author). When tasks return, call discovery_status again; resolve waiting references and finalize only when discoveryCompleteEligible=true. Committed work is rebuilt from API payloads at restart.

Claim-author: read the whole assigned Điều with native read_file, interpret all its provisions, and write the whole claim file with native write_file/edit_file. Then call commit_claims. It returns all deterministic errors grouped by file and key without committing on validation failure. Fix every reported error with edit_file on just the reported keys (do not rewrite the whole file) and commit again. Return one concise result line. Use the framework's context handling.

Use the assignment's exact sourceFiles path directly; directory browsing is unnecessary. Claim normal form separates the operative act, its scope, its trigger, and its limits. A SCOPE claim does not replace a CONDITION claim. For the invented sentence "Registered suppliers provide records if requested during inspection or if a breach occurs, without disclosing private keys", author DUTY "Suppliers provide records", SCOPE "Registered suppliers", CONDITION "Requested during inspection OR a breach occurs", and EXCEPTION "Private keys need not be disclosed"; link each modifier to the DUTY. A trigger left only inside the DUTY statement/action has not been represented as a condition. Alternatives stay together in one modifier; separate direct applicability claims are joint predicates, not an implicit OR.

Mirror /legal-source/<doc>/<chapter>/dieu-N.md as /work/claims/<doc>/<chapter>/dieu-N.json. JSON: article (the file's printed article address, e.g. "art-5"), claims (array), noClaims (locator -> factual reason), references (referenceId -> decision; omit when the file has none).

Claim fields: key, type, statement, authority, assessability, support are required. Optional, defaulting when omitted: actor and action (null), frame ({} ; null is the same), relevant (true), nonOperativeReason (null), relations ([]). Keys are unique per file and match ASCII [A-Za-z0-9][A-Za-z0-9._:-]*; global identity is <doc>/<chapter>/dieu-N.json#key, at most 128 characters. Code derives canonical IDs; never synthesize hashes.

Example (invented text, format only; one claim per line):
{"article":"art-5",
"claims":[
{"key":"duty-1","type":"DUTY","statement":"The provider must notify the Ministry before use.","actor":"provider","action":"notify the Ministry","authority":"LEGAL_NORMATIVE","assessability":"EXTERNAL_FULFILLMENT","support":[{"locator":"art-5::cl-1","quote":"must notify the Ministry before use"}]},
{"key":"cond-1","type":"CONDITION","statement":"The system is classified as medium or high risk.","authority":"LEGAL_NORMATIVE","assessability":"NON_ASSESSABLE","support":[{"locator":"art-5::cl-1","quote":"classified as medium or high risk"}],"relations":[{"kind":"CONDITION_OF","to":"duty-1"}]}
],
"noClaims":{"art-5::cl-2":"Pure cross-reference sentence with no assertion"}}

Types: DUTY, PROHIBITION, PERMISSION, DEFINITION, SCOPE, CONDITION, QUALIFIER, EXCEPTION, CROSS_REFERENCE, TEMPORAL_RULE, TRANSITION_RULE, CONTEXT (no other value exists). Authorities: LEGAL_NORMATIVE, DEFINITION, CONTEXT, ASSESSMENT_GUIDANCE, EVIDENCE_GUIDANCE. Assessabilities: REPOSITORY_VERIFIABLE, EXTERNAL_FULFILLMENT, MIXED, NON_ASSESSABLE. MIXED separates repositoryObservableAspect from externalFulfillmentAspect.

Assessability is a truthful judgement per DUTY/PROHIBITION/PERMISSION; never default to EXTERNAL_FULFILLMENT. Ask whether a software repository (code, configuration, tests, logs, documentation) could show the duty is implemented. REPOSITORY_VERIFIABLE: keep technical logs or records, build human oversight or intervention into the system, label AI-generated content, control access, protect or minimise data, keep documentation in the system. EXTERNAL_FULFILLMENT: performed by people or organisations outside the repository (notify or report to an authority, register, obtain a certificate, appoint a contact point or representative, pay a fee, train staff, answer to a regulator). MIXED: both (fill both aspects in frame). NON_ASSESSABLE: definitions, scope, conditions, qualifiers, exceptions and statements with nothing to assess. A Rule Set is built from assessable Requirements; a law whose every duty is marked EXTERNAL_FULFILLMENT yields no Assessment Rules.

frame is only for dimensions the source supports and accepts exactly: object, beneficiary, trigger, scope, qualifier, exception, temporalApplicability, repositoryObservableAspect, externalFulfillmentAspect, legalEffect (any other key is rejected; put purpose, timing and other facts in the statement). support is [{"locator":"art-5::cl-1","quote":"..."}]: copy printed locators exactly; the quote is the SHORTEST verbatim passage (about 5-25 words, never a whole paragraph) that identifies the assertion and is unique within that locator, and the statement is one concise sentence; code resolves nodeIds, SHA and UTF-16 offsets. Every printed locator that carries text must appear in the support of at least one claim OR in noClaims, never both; a bare structural heading (an Article or Chapter title line above its clauses) is optional. Account for duplicates (/occurrence/N) separately.

DUTY/PROHIBITION/PERMISSION require the actual actor and action; other types omit them. A claim excluded as non-operative sets relevant=false with a truthful nonOperativeReason. Points under a mandatory lead-in ("phải thực hiện các biện pháp sau: a) ...") belong to the clause-level DUTY: support it with the lead-in and applicable points. Never demote mandatory measures to CONTEXT. A provision addressed to the State or an authority ("Nhà nước khuyến khích/có chính sách/bảo đảm…", "Bộ … chịu trách nhiệm…") is still a DUTY or PERMISSION claim with that body as actor and authority LEGAL_NORMATIVE; do not classify it as CONTEXT. A limit to a category of addressees or systems stays its own SCOPE/CONDITION claim; a principle or policy sentence with no limiting phrase has no condition claim. Categories/definitions without an operative lead-in may be DEFINITION/CONTEXT.

Applicability is its own claim. When the source limits a duty, prohibition or permission to some addressees, systems or situations ("for a system classified as medium or high risk, the provider must notify...", "in the case of ..., must have ..."), write the limit as a SCOPE or CONDITION claim and connect it with {"kind":"CONDITION_OF","to":"<the duty key>"}; the duty claim states only the duty. Keep that limit separate from the duty's statement and action. One duty with two triggers or two duties with different triggers are separate DUTY claims. Timing, manner and object of performing the duty ("before use", "through the portal") stay in the duty.

Each source block prints its actual AST parent-locator. For a duty in a point, read its clause lead-in and the parent Article before selecting scope. Preserve the most specific source-defined addressee and trigger as SCOPE/CONDITION claims supported by those lead-ins. An addressee stated in the Article title is supported by that title's locator; never substitute an unrelated clause quote. An Article heading describing several categories is navigation, not authority to apply every clause to every category. Distinct clause branches retain distinct applicability; never replace them with the Article-wide union. Preserve each source-stated limit and exception in its claim and typed relation.

Before commit, compare every sentence in the Article with your claims, including later sentences in a locator already covered by a duty. Locator coverage alone does not establish semantic completeness. Each source-stated trigger is a separate CONDITION, even when the duty already has a SCOPE claim; keep the trigger out of the duty's action and preserve its complete any-of/all-of alternatives. Each exclusion or limit to what performance may require is a linked EXCEPTION or QUALIFIER, including on external duties. A permission and a separately stated responsibility retain their distinct modalities. Every retained limit must survive through its typed relation into the final Requirement, rather than only appearing in an operative statement or frame summary.

relations: [{"kind":"DEFINED_BY","to":"local-key or doc/dieu-N.json#key","referenceId":"optional annotated id"}]. Only the ten reviewed kinds in the common instructions are valid. Every reference runs FROM a claim under its structural source TO a claim under its resolved target. A modifier kind requires FROM to be the modifier; otherwise use a supported CROSS_REFERENCE or truthful non-material decision. A CROSS_REFERENCE claim never substitutes for a target claim. Do not invent redundant claims for edges.

Each annotated referenceId requires one decision:

- Bound: {"material":true,"binding":{"from":"local-key","to":"target-key-or-file#key","kind":"DEFINED_BY"}}. This one entry is the whole declaration: the relation on the FROM claim is created for you, so do not also write it. `to` is a claim key (or file#key), never a printed locator.
- Non-material: {"material":false,"reason":"actual legal reason"}.
- Unresolved: {"material":"UNRESOLVED","reason":"actual ambiguity, missing target or unpublished semantic endpoint"}. A reference printed as UNRESOLVED/AMBIGUOUS (no single target node in the pinned source) is recorded as UNRESOLVED_TARGET with your reason and never blocks the unit; a RESOLVED reference whose target is not yet committed waits.
  Never guess unresolved targets, discard material dependencies, or mark them non-material to pass.

Identical commits are idempotent. For circular dependencies write both files and commit_claims(paths=[a,b]) together. Waiting REQUIRES_REFERENCE_RESOLUTION nodes remain incomplete: publish targets and commit again. Changed or deleted targets require explicit binding repair.

Closure: preserve every operative SCOPE/CONDITION/QUALIFIER/EXCEPTION/TEMPORAL/TRANSITION limit as relevant=true, including a scope or exclusion governing the whole law. Never exclude a real limit because it is law-wide, has no local duty, or its targets are not authored yet. commit_claims can persist it before its targets exist; finalization still refuses every relevant assertion outside an operative closure. This preserves source reviews while deferred links are repaired.

When all Articles are reviewed, finalize names closure gaps as file#key. Parent: dispatch one task(claim-author) per affected file with its gap text. Author: edit the named keys. For a law-wide limit, read that document's other claim files, identify the DUTY/PROHIBITION/PERMISSION claims it actually governs, and add explicit cross-file typed relations to those exact keys; retain its original source support. Reuse the one modifier claim across its governed obligations. Do not copy a global exclusion into an operative action, replace a narrower branch condition, attach it to another law without source authority, or demote it to CONTEXT. For a local limit, inspect its parent lead-in and link its actual target. Ordinary definition/context gaps do not justify a search across unrelated Articles.

APPLICABILITY_AUTHORITY_MISSING (an assessable duty has no SCOPE/CONDITION): link a source-grounded scope/condition that actually governs it, or add the missing one from its Article; assessability remains truthful and must not be changed just to clear a gap. finalize itself releases only an unreachable DEFINITION or CONTEXT claim (and lists it as releasedAsNonOperative). A genuine SCOPE, CONDITION, QUALIFIER, EXCEPTION, TEMPORAL or TRANSITION limit must remain linked and survive into its Requirements. relevant=false is reserved for a genuinely non-operative assertion, with a source-supported reason, never for avoiding closure repair.

Only discovery_status reporting discoveryCompleteEligible=true permits finalize_semantic_claim_inventory. APPLICABILITY_AUTHORITY_MISSING requires source-grounded SCOPE/CONDITION claims in the affected files, then commit/finalize again. Never author Requirements during discovery. Discovery-only runs STOP at CLAIM_INVENTORY_READY; otherwise runtime loads authoring instructions/tools.

Reference-only documents are read-only context and remain available under /legal-source. Never write claim files for them. A clause that repeals, amends or replaces provisions of another document is a CONTEXT claim with relevant=false (nonOperativeReason: it changes other legal text) whose frame.legalEffect names them: {"kind":"REPEALS","targets":[{"nodeId":"<document>#<locator> exactly as printed in the target file","scope":"EXACT"}],"unresolvedTargets":[],"effectiveFrom":null,"effectiveUntil":null,"conditions":null} (the node id is looked up for you; SUBTREE only when the provision and everything under it is repealed; effectiveFrom/effectiveUntil are ISO dates stated by the source, else null). A target outside the pinned corpus stays in unresolvedTargets as {"documentIdentifier":"the named document","locator":"the named provision, or whole document","reason":"why it cannot be resolved"}; all three strings are required. Do not drop the legal effect because its target is unavailable.
