- (decision) Inherit the approved LCSP Figma DS Brand, shared LCSPLogo, shadcn/Base UI primitives, Tailwind v4.3 tokens, Atomic Design boundaries, and bilingual @lcsp/i18n copy; Prompt 8 introduces no new visual brand.
- (decision) Customer financial UX exposes one shared wallet with spendable and outstanding credits; it never presents per-assessment allocations or reservations.
- (decision) PAYMENT_REQUIRED blocks only new paid model invocations, preserves completed work, and routes the customer to top-up; successful payment never resumes an assessment automatically.
- (decision) After top-up, the customer must select Continue; Continue re-checks wallet, pricing, run/lease, and independent runtime/no-progress blockers.
- (decision) Payment blockers, runtime safety blockers, NO_PROGRESS, USAGE_OUTCOME_UNKNOWN, and BILLING_INTEGRITY_REVIEW are distinct states with distinct explanations, actions, and announcements.
- (decision) Customer charge history groups a logical operation and expands separately billable physical retries/fallbacks while excluding prompts, outputs, secrets, and internal margin assumptions.
- (decision) Checkout separates service value, tax, total paid, and credited microcredits; tax never appears as wallet credit.
- (decision) Admin pricing uses exact model, provider default, and optional approved global default coverage with editable versioned cost assumptions, source evidence, suggested tariff, and projected margin preview.
- (decision) Publishing pricing is an explicit immutable action with stale-version, overlapping-interval, missing-rate, and allowlist validation before confirmation.
- (decision) Unknown usage and integrity contradictions route to governed operator queues; compensation is bounded, immutable, and linked to the original debit rather than editing history.
- (decision) Prompt 8 customer/Admin UX is responsive web, desktop-primary, WCAG 2.2 AA, keyboard operable, and uses programmatic status announcements.
- (override) Current UX authority is RBAC with owner/resource scope through assessment.ownerId and wallet.userId; organization membership and PBAC are not active authorization boundaries.
- (assumption) Key screens are specified by spine tables and flow/state contracts; no new pixel mockup is required because the visual system and component library are already approved.
- (event) Prompt 8 PRD, ADR and sprint-change sources reconciled in reconcile-prompt8-authority.md; no approved qualitative decision was dropped.
- (decision) All Prompt 8 financial surfaces remain spine-only because layout behavior is fully specified and the approved LCSP visual system already anchors implementation; optional pixel mockups cannot override the spines.
- (change) Editorial pass clarified Customer versus Manager authority, credited versus spendable value, finalized charge terminology, canonical USAGE_OUTCOME_UNKNOWN, Continue context, blocker ordering, and payment non-effect on integrity review.
- (decision) Keep the mandated assessment-shared-wallet-pricing-ux.md self-contained despite some deliberate overlap with EXPERIENCE.md; add an explicit conflict rule so DESIGN owns visual behavior, EXPERIENCE owns behavior/state, and the Prompt 8 authority document owns scope/traceability/release gates.
- (change) Validation gate remediation aligned component names across both spines, added operational loading/offline/stale/permission matrices, and made Continue rejection states explicit.
- (decision) OUTCOME_UNKNOWN is the canonical domain/API discriminator; customer copy may explain the state in plain language but must not introduce USAGE_OUTCOME_UNKNOWN as a second contract value. No-progress uses NO_PROGRESS_LIMIT_EXCEEDED.
- (decision) Shadow pricing/settlement is Admin-only non-authoritative evidence before DEBIT_ENABLED and cannot alter Customer wallet, history, PAYMENT_REQUIRED, or Continue.
- (decision) CONFIRMED_NO_USAGE requires durable admission-bound proof; operator opinion or missing receipt alone cannot close exposure.
- (decision) Customer totals include only CUSTOMER_WALLET effects; PLATFORM_SPONSORED work never creates Customer debit/outstanding/payment gates.
