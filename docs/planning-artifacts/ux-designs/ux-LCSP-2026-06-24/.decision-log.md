## Decisions

1. Use a quiet operational web-app posture for LCSP.
   - Rationale: LCSP is an evidence-based compliance support product, not a marketing site, chatbot, or consumer assistant.

2. Treat Manager as the primary protagonist and Developer as optional scoped collaborator.
   - Rationale: Phase 5.2L requires Manager-completable golden path without Developer participation.

3. Make evidence gates and blocked states first-class UX objects.
   - Rationale: The product must prevent Wizard-only risk levels, scanner bypass, unsupported legal certainty, and report overclaim.

4. Keep legal corpus administration outside customer product UX.
   - Rationale: Active docs define corpus ingestion/review/approval as internal API/CLI-only for MVP.

5. Carry ChromaDB/vectorless legal RAG into UX only through citation/provenance behavior.
   - Rationale: The backend retrieval path does not change high-level flow, but the UI must show document/article/clause/point citations, corpus version/effective date, primary versus referenced context, expired/superseded warnings, and no citation outside the retrieved allowlist.

6. Exclude structured attestation, manual technical evidence JSON upload, Local/CI scanner report upload, and delegated free-form clarification from active screens.
   - Rationale: Phase 5.2L marks those as superseded, removed, or deferred.

## Resolutions — 2026-07-11 (UX doc audit ahead of MW-web-007/008)

7. Frontend UI system is shadcn/ui (Base UI primitives), confirmed in code (`apps/web/components.json`, `apps/web/src/components/ui`).
   - Rationale: `apps/web/src/app/globals.css` already wires shadcn's CSS variable token set; `DESIGN.md` updated to bind its placeholder tokens to it (see "Token Binding" under Auth Surface) rather than leave the library unconfirmed.

8. Product UI language policy is bilingual (Vietnamese + English), delivered through `@lcsp/i18n`'s parallel `en`/`vi` dictionaries and `resolveMessage()`.
   - Rationale: both locale trees already exist in `packages/i18n/src/locales/{en,vi}`; project rules require every customer-facing string to resolve through `@lcsp/i18n`, which only makes sense as a bilingual (not English-only) commitment.

9. Key-screen HTML/pixel mockups are NOT required for UX approval. The per-page `UI Components`/`UI States` tables already established in `docs/implementation/tasks/modules/web/*.md` (since `MW-web-002`) plus this spine's tokens are the approval bar.
   - Rationale: the task-level tables already carry enough interaction/state detail to implement against; requiring separate mockups would duplicate that content without adding decision-relevant information for this MVP stage.

10. `01-auth-sign-in-page.md`'s shipped implementation deviates from `DESIGN.md`'s "avoid marketing hero layouts... large emotional gradients" rule (split-screen hero panel, undocumented `brand-surface`/`brand-foreground`/`brand-accent` tokens). Added an explicit **Auth Surface** pattern to `DESIGN.md` (centered form card, no hero panel, no new brand-only tokens) so `MW-web-007` (MFA verify) and `MW-web-008` (developer scoped task / accept invitation) do not repeat the drift. `MW-web-001` itself is flagged as a known compliance issue in its task file, pending a follow-up implementation fix.

Changed `{colors.primary}` from teal to blue across `DESIGN.md` ("Primary teal" → "Primary blue") and `apps/web/src/app/globals.css` (`--primary`/`--ring`/`--sidebar-primary` now Tailwind blue-600/blue-500 oklch values in both light and dark; neutral `--background`/`--foreground`/`--secondary`/`--muted`/`--accent`/`--border` re-tinted to a cool blue-gray instead of the previous warm green/cream tint).

## Resolutions — 2026-07-11 (design-taste-frontend skill — scoped adoption)

13. Installed the community skill `sickn33/agentic-awesome-skills@design-taste-frontend` (`.agents/skills/design-taste-frontend/SKILL.md`) per team request, but adopted **only its "anti-generic-AI-tell" guidance**, not its full creative direction. Team decision (asked explicitly, not assumed):
    - **Adopted** (Sections 2, 3 minus Rule 3, 5, 6, 7 of the skill): dependency verification before adding any 3rd-party lib; no emojis in code/copy; `min-h-[100dvh]` never `h-screen` for full-height sections (already the case in `sign-in-page.tsx`); CSS Grid over flex-percentage-math; deterministic/legible system-sans typography (already satisfied — LCSP never used Inter, uses `ui-sans-serif, system-ui, sans-serif`); max 1 accent color, no neon glow, no pure `#000000`, no gradient text, no custom cursors, no oversized screaming H1s; mandatory loading/empty/error states per screen (already the pattern in every `MW-web-*` task's UI Components/States table); animate only `transform`/`opacity`; no filler marketing copywriting ("Elevate", "Seamless", "Unleash") in `@lcsp/i18n` strings.
    - **Rejected** (Sections 4, 8, 9, and Section 3 Rule 3 "anti-center-bias"): bento grids, magnetic/spring-physics buttons, particle effects, liquid-glass refraction, perpetual/infinite micro-animations, kinetic typography, GSAP/ThreeJS scrollytelling, and the ban on centered layouts for auth/utility screens. These are marketing/consumer-SaaS conventions that directly contradict `DESIGN.md`'s "quiet, explicit, evidence-first... avoid marketing hero layouts, decorative illustrations, large emotional gradients" posture and the Auth Surface pattern (Decision #9/#10 above). A centered sign-in form is the correct, expected pattern for an auth screen — not an "AI tell" to be engineered away.
    - **LCSP-specific dial override** (the skill's own `DESIGN_VARIANCE`/`MOTION_INTENSITY`/`VISUAL_DENSITY` baseline of `8/6/4` does NOT apply here): use `DESIGN_VARIANCE ≈ 2` (predictable, symmetric — matches restrained operational density), `MOTION_INTENSITY ≈ 2` (static, `:hover`/`:active` only, plus the existing subtle fade-in on `FormCard` — no perpetual/spring animation), `VISUAL_DENSITY ≈ 5` (normal daily-app spacing; audit/evidence tables may lean denser per `DESIGN.md`'s Data table component, but never "cockpit mode" with mandatory `font-mono` numbers everywhere).
    - Icon library, font family (Geist/Satoshi/Cabinet Grotesk), and other skill-mandated dependency swaps were **not** adopted — LCSP keeps its existing stack (Tailwind v4.3 + shadcn/ui on Base UI + Atomic Design, system font stack) per the Implementation Stack hard constraint; do not add new font or icon packages on the strength of this skill alone.
    - Rationale: the team's actual complaint was the UI looking "too agent/ai-generated" (generic hero panel, invented brand tokens) — already fixed via the Auth Surface pattern and blue palette work (Decisions #10, #12). The skill's anti-cliché checklist is useful for catching future regressions into generic patterns; its marketing/motion arsenal is not relevant to a B2B legal-compliance workbench and must not be applied by default.
