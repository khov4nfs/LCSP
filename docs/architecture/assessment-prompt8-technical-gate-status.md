## G-04 exposure gap found in source review

Before the fix, `RequestBillableInvocationAdmissionHandler` calculated customer exposure by passing only `inputTokensUpperBound` and `outputTokensUpperBound` to the tariff calculator (`apps/api/src/modules/billing/application/commands/request-billable-invocation-admission/request-billable-invocation-admission.handler.ts`). Settlement could additionally price cache reads, cache writes and reasoning (`packages/contracts/src/billing/microcredit-pricing.ts`). The RED E2E proved an ACTIVE tariff with cache-write rate above ordinary input produced an admitted exposure of 3,015 microcredits while an invocation within both token bounds could cost 20,015. The handler now uses `ModelPricingCalculatorService.calculateMaximumExposure` to price every allowed input/cache candidate and retain the maximum; this changes the pre-dispatch risk bound, not the actual usage charge.

Remaining G-04 work: verify for each enabled provider whether its input cap includes cache read/write and whether its output cap includes reasoning. The current calculation assumes these buckets fit within the corresponding route token limits. Capture real provider usage examples, add property/boundary checks for every approved rate policy, measure rejected slots and exposure outcomes during a soak, then obtain policy-owner approval. Do not silently raise an existing admission's exposure after dispatch or mark G-04 GREEN from the current tests.
